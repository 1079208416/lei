# 外卖平台 MVP 技术方案

## 1. 文档信息

| 项目 | 内容 |
| --- | --- |
| 文档名称 | 外卖平台 MVP 技术方案 |
| 文档版本 | V1.0 |
| 对应产品 | 单城市、多商户、平台型外卖 |
| 目标阶段 | 首批真实用户和商户试点 |
| 技术策略 | Java 模块化单体，前端多端复用 |

> 实现说明：当前可运行版本以 Java 17 LTS 为目标版本，兼容 Java 21 环境；前端采用一个 Vue 3 应用承载用户、商家、骑手和运营四种角色工作区。微信支付、地图和短信暂以开发模拟及可替换适配层实现。

## 2. 技术目标

本方案需要支撑产品设计文档中的用户端、商家端、骑手端和平台后台，完成以下闭环：

1. 用户浏览商家、点餐、支付和查看订单。
2. 商家接收订单、接单、出餐和处理异常。
3. 平台人工派单，骑手完成取餐和送达。
4. 平台处理取消、退款、售后和基础运营配置。

### 2.1 设计原则

- 首版采用模块化单体，不拆分微服务。
- MySQL 是业务数据的唯一事实来源。
- 订单状态变更必须集中管理并支持幂等。
- 外部支付、地图和短信调用必须设置超时和失败处理。
- 优先保证交易闭环和异常处理，不提前建设高并发架构。
- 一套后端服务同时服务四个端，通过角色和数据权限隔离。

### 2.2 首版规模假设

- 单城市或单运营区域。
- 试点商户 3 至 10 家。
- 每日订单量控制在人工运营可以覆盖的范围内。
- 首版按单实例部署设计，后续可通过水平扩展和缓存优化扩容。

## 3. 总体架构

```text
┌─────────────────┐  ┌─────────────────┐  ┌─────────────────┐  ┌─────────────────┐
│ 用户微信小程序  │  │   商家移动 H5   │  │   骑手移动 H5   │  │  平台运营后台   │
└────────┬────────┘  └────────┬────────┘  └────────┬────────┘  └────────┬────────┘
         │                    │                    │                    │
         └────────────────────┴─────────HTTPS/WS───┴────────────────────┘
                                      │
                                    Nginx
                                      │
                         ┌────────────┴────────────┐
                         │ Spring Boot 模块化单体  │
                         │ 业务模块 / WebSocket    │
                         │ 定时任务 / 集成适配器   │
                         └────────────┬────────────┘
                                      │
          ┌───────────────┬───────────┼───────────┬───────────────┐
          │               │           │           │               │
        MySQL           Redis      COS/OSS     腾讯位置服务     微信支付
```

### 3.1 架构说明

- 四端通过统一的 HTTPS API 访问后端。
- 商家订单提醒、骑手任务提醒和用户订单状态使用 WebSocket。
- 用户支付、退款和订单超时由后端定时任务及支付回调处理。
- Redis 用于验证码、登录态、短期缓存和限流，不作为业务数据源。
- 图片存储在对象存储中，数据库只保存文件地址。
- 微信支付、地图、短信和对象存储通过独立集成模块接入。

后端与前端可以单独构建和部署。用户端、商家端和骑手端共用接口类型及通用逻辑，但不强行共用页面组件。

## 6. 后端模块划分

后端采用领域模块化单体，模块之间通过应用服务或领域事件协作，不允许直接修改其他模块的核心数据。

| 模块 | 主要职责 |
| --- | --- |
| common | 统一响应、异常、枚举、工具、分页和通用校验 |
| auth | 登录、令牌、角色、权限和验证码 |
| user | 用户资料、收货地址和用户状态 |
| merchant | 商户资料、营业状态、配送范围和商家账号 |
| catalog | 商家分类、商品分类、商品、规格、加料和库存 |
| cart | 购物车、价格试算和下单前校验 |
| order | 订单创建、订单快照、状态机、取消和查询 |
| payment | 支付单、微信支付、回调、超时和对账 |
| delivery | 配送区域、配送费、骑手任务和人工派单 |
| aftersale | 售后申请、退款审核和退款记录 |
| notification | WebSocket 消息、微信订阅消息和短信任务 |
| admin | 平台运营、查询、配置、报表和操作日志 |
| integration | 微信支付、腾讯位置服务、短信和对象存储适配 |

### 6.1 后端分层

每个业务模块内部按照以下层次组织：

```text
controller      接收请求、参数校验和响应转换
application     编排业务用例和事务边界
domain          订单状态机、金额和核心业务规则
infrastructure  数据库、外部服务、缓存和消息实现
```

控制器不直接操作数据库，订单、支付和退款等核心规则放在应用服务和领域对象中。

### 6.2 模块依赖原则

- `order` 是订单生命周期的唯一管理模块。
- `payment` 只管理支付和退款渠道，不直接修改订单明细。
- `delivery` 只管理配送任务，不直接修改订单金额。
- `merchant` 和 `catalog` 为订单提供下单校验和商品快照来源。
- 跨模块状态变更通过应用服务接口完成，并记录状态日志。
- 通用基础能力放入 `common`，避免各模块重复实现。

## 7. 前端方案

### 7.1 用户端

主要页面：

- 登录和手机号授权。
- 定位与地址选择。
- 首页商家列表、分类和搜索。
- 商家详情、菜单、商品规格和购物车。
- 确认订单、支付和支付结果。
- 订单详情、配送状态和历史订单。
- 取消、退款和客服入口。
- 个人中心、地址管理和协议页面。

用户端通过微信登录获取身份，通过腾讯位置服务选择地址，通过微信支付完成付款。用户端不保存商品价格和最终金额，所有金额以后端计算结果为准。

### 7.2 商家端

主要页面：

- 登录和店铺状态。
- 新订单、进行中订单和历史订单。
- 订单详情、接单、拒单和出餐操作。
- 分类、商品、规格和库存管理。
- 店铺营业时间、公告和联系电话。
- 当日经营数据和商品销量。

商家端使用 WebSocket 接收新订单，并播放提示音。WebSocket 断开时通过轮询获取新订单。

### 7.3 骑手端

主要页面：

- 登录和任务列表。
- 待取餐、配送中和历史任务。
- 取送地址、联系人和订单备注。
- 调用第三方地图导航。
- 确认取餐、确认送达和异常上报。

首版地图只用于地址展示和导航跳转，不绘制实时配送轨迹。

### 7.4 平台运营后台

主要页面：

- 数据概览。
- 商户审核和商户管理。
- 用户、订单和售后查询。
- 人工派单、改派和配送异常处理。
- 配送区域、配送费和基础参数配置。
- 平台账号、角色权限和操作日志。

### 7.5 前端公共约定

- 统一封装请求、错误提示、登录失效和重试。
- 所有金额使用“分”作为接口单位，页面负责显示格式。
- 所有列表支持统一分页结构。
- 所有关键操作显示处理中、成功和失败状态。
- 商家端和骑手端优先保证弱网下的可操作性。

## 8. 身份认证与权限

### 8.1 登录方式

| 角色 | 登录方式 |
| --- | --- |
| 用户 | 微信登录，绑定手机号 |
| 商家 | 平台创建账号，手机号加密码或验证码登录 |
| 骑手 | 平台创建账号，手机号加密码或验证码登录 |
| 运营与客服 | 后台账号密码登录 |

后台管理员后续可增加二次验证，MVP 先保证账号、密码和角色权限。

### 8.2 权限模型

采用简化 RBAC 模型：

- 用户只能访问自己的地址、购物车和订单。
- 商家只能访问所属商户的订单、商品和经营数据。
- 骑手只能访问分配给自己的配送任务。
- 运营可以访问全平台订单和商户数据。
- 客服可以查询订单和处理售后，但不能修改系统配置和商户结构。
- 超级管理员拥有全部权限。

除接口权限外，服务端必须根据当前用户 ID、商户 ID 和骑手 ID 进行数据级隔离。

### 8.3 令牌与安全

- 使用短期 Access Token 和较长有效期 Refresh Token。
- 登录态和令牌黑名单存入 Redis。
- 验证码设置有效期、发送间隔和次数限制。
- 密码使用 BCrypt 或 Argon2 哈希存储。
- 支付密钥、短信密钥和数据库密码通过环境变量注入，不写入代码仓库。

## 9. 核心业务流程设计

### 9.1 订单状态建模

订单履约状态、支付状态和退款状态分开保存，避免一个字段同时表达多种业务含义。

订单主状态：

```text
WAITING_PAYMENT -> WAITING_ACCEPT -> PREPARING -> WAITING_PICKUP
                -> DELIVERING -> COMPLETED
```

其他结束状态：

```text
WAITING_PAYMENT -> CANCELLED
WAITING_ACCEPT  -> CANCELLED
WAITING_ACCEPT  -> REJECTED
```

支付状态：

```text
UNPAID -> PAYING -> PAID -> REFUNDING -> REFUNDED
                 -> FAILED
```

退款状态由售后单独立记录。已完成订单仍可进入售后流程，不影响原订单的履约状态。

### 9.2 创建订单

1. 客户端提交商户、商品、规格、数量和地址。
2. 后端校验商户营业状态和配送范围。
3. 后端重新读取商品价格、规格和可售状态。
4. 后端重新计算商品金额、打包费和配送费。
5. 生成订单、订单明细、地址快照和状态日志。
6. 创建支付单并返回微信支付参数。

关键规则：

- 不信任客户端传入的价格和优惠金额。
- 商品名称、规格和价格写入订单明细快照。
- 创建订单使用幂等令牌，防止重复提交。
- 订单和明细在同一个数据库事务中创建。
- 外部支付调用不放在数据库事务中执行。

### 9.3 库存处理

食品外卖首版优先使用“是否售罄”而不是复杂库存扣减。

- 商家可将商品标记为售罄。
- 下单时校验商品处于可售状态。
- 如需数量库存，支付成功后使用条件更新扣减库存。
- 库存不足时自动取消订单并发起退款。
- 不采用支付前长时间锁定库存的方式。

### 9.4 支付回调

1. 微信支付调用后端回调接口。
2. 后端验证签名、金额和商户信息。
3. 根据微信交易号保证回调幂等。
4. 更新支付单为已支付。
5. 将订单从待支付变更为待接单。
6. 通知商家端和用户端。

支付回调必须支持重复通知，同一交易号重复到达时只处理一次。

### 9.5 商家接单

- 商家接单时校验订单仍处于待接单状态。
- 使用条件更新将状态改为制作中。
- 更新失败视为订单已被其他操作处理。
- 商家拒单时记录原因，订单进入拒单状态并创建退款。
- 商户超时未接单时只提醒运营，不在首版自动取消。

### 9.6 人工派单

1. 订单进入待取餐后出现在运营后台。
2. 运营选择在线骑手并创建配送任务。
3. 骑手端通过 WebSocket 收到任务。
4. 骑手确认取餐，订单进入配送中。
5. 骑手确认送达，订单进入已完成。

一个订单同一时刻只能有一个有效配送任务。改派时需要先关闭原任务，再创建新任务，并记录操作日志。

### 9.7 取消与退款

- 待支付订单由用户取消或超时任务取消。
- 待接单订单可在支付后由用户申请取消。
- 商户拒单、缺货或平台取消时自动创建整单退款。
- 退款请求使用业务幂等号，防止重复退款。
- 退款成功后更新支付和售后状态，并通知用户。
- 配送中的订单原则上由平台客服处理，不开放用户直接取消。

### 9.8 订单超时

首版使用定时任务扫描已到期的未支付订单：

- 通过订单状态和过期时间建立索引。
- 每次分批处理，避免一次加载过多数据。
- 使用条件更新关闭订单。
- 关闭后释放相关购物车和临时状态。

## 10. 数据库设计

### 10.1 通用约定

- 所有金额字段使用整数，单位为分。
- 所有表包含主键、创建时间和更新时间。
- 订单号使用独立业务编号，数据库主键可使用雪花 ID。
- 状态字段使用短字符串枚举，不使用含义不明的数字。
- 重要业务表保留状态日志，禁止只覆盖最终状态。
- 时间统一按服务端时间生成，前端时区用于展示。

### 10.2 主要数据表

| 数据表 | 主要内容 |
| --- | --- |
| `app_user` | 微信标识、手机号、昵称、状态 |
| `user_address` | 用户地址、联系人、经纬度和默认标记 |
| `merchant` | 商户资料、营业时间、坐标、配送范围和状态 |
| `merchant_account` | 商家登录账号和所属商户 |
| `rider` | 骑手资料、账号和在线状态 |
| `rider_account` | 骑手登录账号 |
| `product_category` | 商家商品分类和排序 |
| `product` | 商品名称、图片、基础价格和上下架状态 |
| `product_option_group` | 规格或加料分组 |
| `product_option` | 规格选项和加价 |
| `cart_item` | 用户、商户、商品、规格和数量 |
| `t_order` | 订单号、用户、商户、状态、金额和过期时间 |
| `order_item` | 商品、规格、单价、数量及快照 |
| `order_status_log` | 订单状态、操作角色和时间 |
| `payment_record` | 支付渠道、交易号、金额和状态 |
| `refund_record` | 退款单号、退款金额、原因和状态 |
| `delivery_task` | 订单、骑手、取送地址和配送状态 |
| `delivery_status_log` | 配送任务状态变更记录 |
| `delivery_area` | 配送区域、中心点、半径和配送费规则 |
| `after_sale` | 售后原因、凭证、审核和处理结果 |
| `notification_task` | 待发送通知、重试次数和发送结果 |
| `operation_log` | 后台关键操作、操作人、对象和时间 |
| `platform_config` | 超时时间、提醒阈值和平台基础参数 |

### 10.3 关键索引

- 用户订单：`user_id + created_at`。
- 商户订单：`merchant_id + status + created_at`。
- 超时订单：`status + expire_at`。
- 支付交易号唯一索引。
- 退款业务幂等号唯一索引。
- 配送订单唯一有效任务索引。
- 商家账号和骑手账号唯一索引。

### 10.4 状态并发控制

订单、支付和配送状态更新使用以下方式之一：

- 使用带原状态的条件更新。
- 使用版本号进行乐观锁更新。

如果更新影响行数为零，业务层返回“订单状态已变化”，不得覆盖最新状态。

## 11. API 设计

### 11.1 路径约定

```text
/api/user/v1/**       用户端接口
/api/merchant/v1/**   商家端接口
/api/rider/v1/**      骑手端接口
/api/admin/v1/**      运营后台接口
/api/payment/**       支付回调接口
/ws/**                WebSocket 连接
```

### 11.2 响应约定

统一响应结构：

```json
{
  "code": "SUCCESS",
  "message": "ok",
  "data": {},
  "requestId": "request-id"
}
```

- 业务错误返回稳定错误码，前端负责转换成用户提示。
- 分页接口统一使用 `page`、`pageSize`、`total` 和 `items`。
- 创建订单、支付、退款和派单接口支持幂等键。
- 所有接口通过 Springdoc OpenAPI 生成文档。

### 11.3 接口权限

- 每个端使用独立路径前缀和角色权限。
- 服务端从令牌读取身份，不接受客户端传入的用户或商户身份作为可信参数。
- 商家和骑手访问详情时必须校验数据归属。
- 支付回调只接受合法签名请求。

## 12. 实时通知与消息

### 12.1 WebSocket

- 商家连接后订阅本商户订单事件。
- 骑手连接后订阅本人配送任务事件。
- 用户连接后订阅本人订单状态事件。
- 连接时进行身份认证和权限校验。
- 客户端断线自动重连，重连后拉取最新状态。
- 商家端保留轮询作为新订单备用通知方式。

### 12.2 通知任务

微信订阅消息和短信通过 `notification_task` 表记录：

- 业务事件产生通知任务。
- 定时任务扫描并调用外部服务。
- 发送失败按次数重试。
- 达到最大次数后标记失败并写日志。

MVP 阶段不引入消息队列，使用数据库任务表即可满足试点规模。

## 13. 外部服务集成

### 13.1 微信登录与支付

- 用户端使用微信登录换取业务登录态。
- 支付使用微信支付 API v3。
- 平台统一收款，商家结算在线下完成。
- 支付回调和退款回调必须验签。
- 支付金额以服务端订单金额为准。

### 13.2 地图与配送范围

- 使用腾讯位置服务完成地址搜索和坐标转换。
- 商户保存经纬度，配送区域首版使用中心点加半径。
- 下单时根据用户地址坐标判断是否在配送范围内。
- 第三方地图异常时不阻塞已有订单处理，但需要给出明确提示。

### 13.3 文件与短信

- 图片通过签名地址直接上传对象存储。
- 后端只保存文件 URL 和业务归属。
- 短信验证码和重要订单通知由集成模块统一发送。
- 所有外部调用必须设置连接超时和读取超时。

## 14. 部署方案

### 14.1 环境划分

- `dev`：本地开发环境。
- `test`：联调和验收环境。
- `prod`：试点生产环境。

支付、短信和地图使用独立测试配置，禁止测试环境调用生产密钥。

### 14.2 生产部署

```text
Internet
   |
 Nginx + HTTPS
   |
 Spring Boot 应用
   |
 MySQL + Redis + COS/OSS
```

- 前端 Web 资源由 Nginx 提供静态访问。
- 小程序通过备案域名访问后端 API。
- 后端和 Nginx 使用 Docker Compose 部署。
- MySQL 和 Redis 优先使用云托管服务。
- 每日执行数据库备份并定期验证恢复流程。

### 14.3 配置管理

- 使用环境变量管理数据库、Redis、JWT、支付和地图密钥。
- 仓库中只保留 `.env.example`。
- 生产配置和测试配置分离。
- 日志中不得输出完整手机号、地址、令牌和支付密钥。

## 15. 安全与合规

- 所有生产接口使用 HTTPS。
- 登录、验证码、支付和退款接口增加频率限制。
- 对输入参数进行长度、格式和业务状态校验。
- 防止越权访问，不能只依赖前端隐藏入口。
- 退款、派单、商户停用和权限修改记录操作日志。
- 用户隐私数据只用于订单履约和客服处理。
- 定期清理过期验证码、登录态和临时数据。
- 对支付金额、订单号和交易号进行一致性校验。

## 16. 测试与验收

### 16.1 后端测试

- 订单状态机的正常和非法流转。
- 创建订单的价格计算和商品快照。
- 重复提交和支付回调幂等。
- 商户拒单、超时未支付和退款流程。

- 配送任务唯一性和改派流程。

### 16.2 前端与联调测试

- 用户从登录到支付成功的主流程。
- 商家新订单提醒、接单、拒单和出餐。
- 后台人工派单、改派和退款。
- 骑手取餐、送达和异常上报。
- WebSocket 断线重连和轮询降级。

### 16.3 技术验收标准

- 用户能够完成完整下单和支付流程。
- 商家能够稳定接收并处理订单。
- 平台能够人工派单并追踪配送状态。
- 支付回调和退款请求不会重复执行。
- 订单状态不会因并发操作被覆盖。
- 四端权限和数据范围隔离有效。
- 关键业务操作可查询日志。
- 核心流程具备自动化或可重复的手工验收用例。

## 18. 首版技术边界

首版不建设以下能力：

- 微服务拆分、服务注册和配置中心。
- Kafka、RabbitMQ 等独立消息中间件。
- Kubernetes 和复杂容器编排。
- 智能派单、骑手抢单和路径规划。
- 实时地图轨迹和复杂围栏。
- 商家自动分账和在线结算。
- 商品级部分退款和复杂售后仲裁。
- 优惠券、会员、积分和营销引擎。
- 多城市数据隔离和复杂多租户。

## 19. 主要风险与应对

| 风险 | 应对方式 |
| --- | --- |
| 支付回调和退款重复执行 | 外部交易号唯一约束、幂等处理和状态条件更新 |
| 商家漏单或未及时接单 | WebSocket 加轮询、声音提醒、运营超时监控 |
| 地图定位和地址不准确 | 允许用户手动修正地址，保存坐标并人工兜底 |
| 并发修改订单状态 | 条件更新或乐观锁，禁止无校验覆盖 |
| 外部服务短暂不可用 | 超时、重试、任务表和人工处理入口 |
| 试点订单量突增 | 单实例加索引、缓存和监控，按实际瓶颈再扩展 |
| 小程序审核和支付资质延迟 | 尽早准备主体资质、支付商户号和域名备案 |

## 20. 总结

该技术方案以 Spring Boot 模块化单体为核心，通过 Vue 3 多端前端覆盖四个业务角色，使用 MySQL、Redis、对象存储和微信生态服务完成 MVP 闭环。

首版最重要的技术目标是订单、支付、退款和配送状态可靠，而不是追求高并发或微服务化。试点验证后，再根据实际订单量、团队规模和业务瓶颈决定是否拆分服务、引入消息队列或建设智能调度。
